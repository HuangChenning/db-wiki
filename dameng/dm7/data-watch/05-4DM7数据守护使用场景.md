本章介绍`DM7`数据守护系统的各种使用场景，包括正常运行和各种异常情况的处理场景。`DM7`数据守护系统包括较多的部件，每一个部件都有可能发生故障，因此异常的类型较多，本章介绍的使用场景包括：

- 数据守护系统正常运行
- 切换主备机
- 主数据库故障处理
- 备数据库故障处理
- 主机故障处理
- 备机故障处理
- 主机公共网络故障处理
- 内部网络故障处理
- 备机接管
- 强制`OPEN`主机
- 滚动升级
- 故障数据恢复

## 4.1 数据守护系统正常运行

搭建完成的数据守护系统主数据库对外提供一切正常的数据库服务，用户还可以登录备数据库进行数据查询操作。只要数据守护系统的数据库不发生异常，且所有硬件和网络都正常，那么对于用户来说，应用在主数据库上的操作与在单机版`DM7`数据库的操作没有什么区别。

在数据守护系统正常运行时，主数据库将产生的`REDO`日志通过网络传递到备数据库，备数据库解析并重做`REDO`日志，实现备数据库与主数据库之间的数据同步。这样，当主数据库发生异常时，数据守护系统才能迅速将备机切换为主机继续对外提供服务，实现系统的高可用性。

下面各小节介绍数据守护系统运行时可能遇到的各种情景。

## 4.2 切换主备机

现在，主备机切换已经完成了，`DM2`成为了主数据库而`DM1`成为了备数据库。应用系统原本是连接在主数据库上进行操作的，现在主备机进行了切换，应用系统就需要连接新的主数据库。为了，解决这个问题，`DM7`提供了应用故障自动重连功能。

- 故障自动重连

配置`DM7`数据守护，一般要求应用在使用的数据库接口中配置连接服务名，以实现故障自动重连。连接服务名可以在`DM7`提供的各接口驱动程序中使用，连接数据库时指定连接服务名，接口会随机选择一个`IP`进行连接，如果连接不成功或者服务器状态不正确，则顺序获取下一个`IP`进行连接，直至连接成功或者遍历了所有`IP`。

用户可通过编辑`dm_svc.conf`文件来配置连接服务名。`dm_svc.conf`配置文件在`DM7`安装时生成，`Windows`平台下位于`%SystemRoot%\system32`目录，`Linux`平台下位于`/etc`目录。

连接服务名配置格式：

```
SERVERNAME=(IP[:PORT],IP[:PORT],......)
```

配置项目说明：

- `SERVERNAME`：连接服务名，用户通过连接服务名访问数据库
- `IP`：数据库所在的`IP`地址，如果是`IPv6`地址，为了区分端口，需要用`[]`封闭`IP`地址
- `PORT`：数据库使用的`TCP`连接端口，可选配置，不配置则使用连接上指定的端口

另有下列几个参数：

```
LOGIN_PRIMARY=(1/0)
SWITCH_TIME=(val)
SWITCH_INTERVAL=(val)
```

用来配置在服务器之间切换连接，它们可配合`SERVERNAME`参数一起使用。

`1) LOGIN_PRIMARY`表示是否仅登录到主机，支持的选项为1（只连接主机）和0（主机不存在的情况下可连接备机）。可以不指定，若不指定，默认值为1；

`2) SWITCH_TIME`表示在服务器之间切换的次数，有效值范围`1~9223372036854775807`，默认值为3；

`3) SWITCH_INTERVAL`表示在服务器之间切换的时间间隔，单位为毫秒，有效值范围`1~9223372036854775807`，默认值为200；

这里我们配置一个名为`dw_svc`的连接服务名，使用`dw_svc`连接数据守护中的数据库，即可实现故障自动重连。

```
dw_svc=(192.168.1.131:5236,192.168.1.132:5236)
```

## 4.3 主数据库故障处理

当数据守护系统的主数据库发生故障时，未提交的活动事务会被强制回滚。数据守护系统的处理分为两种情况：非自动切换模式和自动切换模式。

- 非自动切换模式

如第2章中所配置的，`dmwatch.ini`中参数`DW_FAR_ERROR_TIME`置为0时，表示数据守护系统为非自动切换模式。

非自动切换模式下，若主数据库异常关闭，如果配置了主机自动重启（`dmwatch.ini`的参数`INST_AUTO_RESTART`置为1），则守护进程会将数据库实例自动重新启动，能够继续对外服务，主备实例的模式不会发生改变；如果没有配置主机自动重启，则主数据库实例不会自动重启，只有备机能继续提供对外的只读服务，用户可以手动重启或者通过第三方`HA`软件等重启，或者使用监视器进行备机接管主机。

- 自动切换模式

若将`dmwatch.ini`中参数`DW_FAR_ERROR_TIME`置为非0的合法值，数据守护系统处于自动切换模式。

如果主数据库异常关闭，系统自动将备数据库切换为主数据库，继续对外提供数据库服务。若配置了数据库实例自动重启（`dmwatch.ini`的参数`INST_AUTO_RESTART`置为1），守护进程会重启异常关闭的数据库；若没有配置数据库实例自动重启，则需要手动重启异常关闭的数据库。之后数据守护系统会为重新启动的数据库实例同步历史数据，重新作为备数据库加入数据守护系统中，这个过程是完全自动的，不需要用户干预。

## 4.5 主机故障处理

- 非自动切换模式

在非自动切换模式下，当数据守护系统的主机发生故障时，备机会继续对外提供只读服务。用户可以在排除主机故障后手动重启或者通过第三方`HA`软件等重启主数据库，或者使用监视器进行备机接管主机。

- 自动切换模式

在自动切换模式下，如果数据守护系统的主机出现故障，系统会自动将备机切换为主机，继续对外提供服务。主机故障处理的过程，涉及守护进程状态变换，将备数据库从`STANDBY`模式切换为`PRIMARY`模式，以及数据库状态转换等步骤。具体处理流程包括（假定`DW_P`为主机，`DW_S`为备机）：

`1. DW_P`故障；

`2. DW_S`守护进程没有收到`DW_P`守护进程的广播消息，认定`DW_P`出现故障；

`3. DW_S`守护进程切换为`FAILOVER`状态；

`4. DW_S`守护进程确认接收到的所有`REDO`日志重做完成；

`5. DW_S`守护进程`MOUNT`数据库；

`6. DW_S`守护进程将数据库切换为`PRIMARY`模式；

`7. DW_S`守护进程将数据库的日志实时归档失效；

`8. DW_S`守护进程重新`OPEN`数据库，`OPEN`数据库过程中，在`DW_P`数据库上的未提交事务被全部回滚；

`9. DW_S`守护进程重新切换为`OPEN`状态。

至此，主机故障切换完成，备数据库切换为主数据库，继续对外提供正常数据库服务。

## 4.6 备机故障处理

若数据守护系统的备机出现故障，主数据库会自动将日志实时归档失效，并继续提供正常的数据库服务。具体处理流程包括（假定`DW_P`为主机，`DW_S`为备机）：

`1. DW_S`故障；

`2. DW_P`守护进程没有收到`DW_S`守护进程的广播消息，认定`DW_S`故障；

`3. DW_P`守护进程切换为`FAILOVER`状态；

`4. DW_P`守护进程`SUSPEND`数据；

`5. DW_P`守护进程将数据库的日志实时归档失效；

`6. DW_P`守护进程重新`OPEN`数据库。

至此，备机故障处理完成，主数据库继续对外提供正常数据库服务。

## 4.7主机公共网络故障处理

- 非自动切换模式

当主机公共网络发生连接故障时，若数据守护系统为非自动切换模式，系统管理员应根据应用情况和故障情况作出对应的判断处理。如果主机公共网络故障可以较快解决，且允许主机暂时中断对外服务，则尽快排出网络故障即可；否则的话需要手动进行备机接管。

- 自动切换模式

数据守护系统的主机守护进程会自动检测主机的公共网络，若主机发生公共网络故障，且数据守护系统处于自动切换模式，主机守护进程会强制关闭主数据库，备机守护进程切换备数据库为主数据库，继续对外提供服务。

续上节，当前数据守护系统的状态是只有`DM2`作为主机对外提供服务。启动`DW_P`，启动备机上的守护进程，数据守护系统恢复正常。系统当前状态是，`DW_P`为备机，`DM1`为备数据库，`DW_S`为主机，`DM2`为主数据库。

停止主机公共网卡服务：

```
ifdown eth1
```

`DW_S`的守护进程检测到主机公共网络故障后，强制关闭`DM2`，备机`DW_P`切换为主机，之后`DW_S`的守护进程自动重启`DM2`，并将`DM2`作为备数据库重加入守护系统。

监视器打印的主备机切换过程与“主数据库故障处理”的相同，这里不再赘述。

## 4.8内部网络故障处理

- 非自动切换模式

数据守护系统为非自动切换模式时，若发生内部网络故障，系统管理员应根据故障现象仔细确认故障点，并修复网络故障。

如果主机与备机之前的内部网络出现故障，备数据库无法收到主数据库发来的日志，备机守护进程认为主机出现故障。但此时主机能正常运行并对外提供数据库服务，主机会将日志实时归档置为失效。管理员在确认故障后只需要及时修复网络故障，守护系统会自动进行后续处理，同步历史数据到备机。

如果主机与监视器或备机与监视器之间的网络出现故障，并不会影响守护系统的运行，管理员只需及时修复网络故障就可继续使用监视器对数据守护系统进行管理。

- 自动切换模式

自动切换模式下`,DM7`数据守护对内部网络的可靠性提出了很高的要求，但是在某些情况下（比如异地容灾），存在很多不可控因素，导致内部网络无法保证绝对可靠。针对这种情况，我们强烈建议为守护系统配置一个确认监视器，由确认监视器与守护进程的信息共同决定故障处理流程。

假设在自动切换模式下，没有配置确认监视器，当内部网络一切正常时系统可以正常运行。可是当主、备机之间的内部网络出现故障时，备机守护进程认为主机出现故障，将自己切换为主机。可是此时主机实际上是正常运行的，就出现了数据守护系统的双主机现象。此时若有用户分别连接到两个主机进行数据库操作，则会造成两个主机数据不一致，数据守护系统的数据将被破坏。

如果为数据守护系统配置了确认监视器，情况就不一样了。当主、备机之间的内部网络出现故障时，备机守护进程认为主机出现故障，会将自己的状态转换为`CONFIRM`状态，等待确认监视器发来的信息。收到确认监视器发来的消息，得知主机并未故障，备机不会切换为主机，而是重新将自己转换为`OPEN`状态。

## 4.9备机接管

在非自动切换模式下，确认主机故障后，用户可在监视器上执行`TAKEOVER`命令，启动备机接管。为了确保接管后主备机的数据一致，`TAKEOVER`的条件比较严格，分以下两种情况：

1. 主机故障，`dmserver/dmwatch`都无法访问，此时备机必须同时满足以下三个条件
- 备机正常，`dmserver/dmwatch`都正常
- 备机必须曾经接受过主机的广播消息
- 备机的`dmwatch`保存的最后一次主机`dmatch`的消息中，主机状态正常且归档有效，主机的`file_lsn`小于备机的`cur_lsn`
2. 主机`dmserver`故障，主机`dmwatch`正常，此时还必须满足以下两个条件
- 备机正常，`dmserver/dmwatch`都正常
- 主机`dmwatch`不是`ERROR`或`SHUTDOWN`状态，且主机实例状态为`ERROR`

因此用户在执行备机接管时，必须严格按照以下步骤执行：

`1)` 确认主机故障

检查主机的`dmserver/dmwatch`同时无法访问，或主机的`dmserver`无法访问，是由于主机故障而非网络故障或其他原因引发，防止主机处于异步归档状态。

`2)` 查询备机确认能否接管

启动命令行工具`disql`，登录备数据库库，执行：

```
SELECT SF_DW_CHECK_TAKEOVER();
```

系统函数返回1代表可以接管；0表示不能接管。

`3)` 在监视器上执行`TAKEOVER`接管命令

```
TAKEOVER
```

## 4.10强制OPEN主机

在某些情况下，数据守护系统中的备机会暂时无法提供服务（如地震、水灾导致备机损毁；或者用户暂时不希望启动备机）。正常情况下，主机可以自动将实时归档失效，继续对外提供服务。但如果在此期间，主机由于某种原因也需要重启，重启后守护进程获取不到备机的日志信息，无法判断主备机之间的数据同步情况；因此，在这种情况下守护进程`dmwatch`无法自动`OPEN`主机`dmserver`实例，`dmserver`会一直保持`Mount`状态，无法对外提供数据库服务。

此时，必须要有用户的人工干预，手工强制启动主机，以继续提供数据库服务。有两种方法可以强制`OPEN`主机：

- 在监视器上执行`OPEN FORCE`命令
- 直接登录主数据库执行`SQL`命令强制`OPEN`

注意：强制`OPEN`主机存在一定风险，用户需要确认以下事项，避免损坏数据：

- 备机实例未启动，并且没有执行过`TAKEOVER`操作，仍然保持`STANDBY`状态
- 不是由于网络故障导致无法获取备机信息
- 由于监视器执行`OPEN FORCE`命令会进行一系列的校验，可以降低出错概率，建议使用`OPEN FORCE`命令强制启动主机，不建议直接使用`SQL`命令强制启动主机
- 在监视器上执行`OPEN FORCE`

监视器`dmwmon`提供了`OPEN FORCE`命令强制`OPEN`主机。该命令能执行的条件是备机及其守护进程故障，主机实例处于`Mount`或`Suspend`状态，主机`dmwatch`处于`STARTUP`状态。此命令只在非自动切换模式下有效。


## 4.11滚动升级

`DM7`数据守护作为一个高可用解决方案，其应用往往需要保证`7*24`小时运行，当需要进行数据库版本升级时，也需要能提供一个在线升级方案。`DM7`数据守护可以确保数据库服务不中断的情况下实现滚动升级。

假定初始状态为主机`DW_P`，主数据库`DM1`，备机`DW_S`，备数据库`DM2`，监视机`DW_M`，滚动升级操作步骤如下：

1. 关闭DW_S守护进程，正常关闭DM2；这个过程中，DW_P守护进程会检测到DW_S故障，并进行故障处理，关闭REDO日志实时归档；
2. 升级DW_S，重新安装新版本服务器，或者直接将新的执行程序和动态库替换旧版本；
3. 启动DW_S守护进程，DW_S守护进程重启DM2；
4. 等待历史数据同步完成，DW_S重新加入数据守护系统（可以通过监视器DW_M查看数据守护系统是否恢复正常）；
5. 关闭DW_P守护进程，正常关闭DM1；这个过程中，DW_S会检测到DW_P故障，并进行故障处理，将DW_S切换为主机；
6. 升级DW_P，重新安装新版本服务器，或者直接将新的执行程序和动态库替换旧版本；
7. 启动DW_P守护进程，DW_P守护进程重启DM1；
8. 等待历史数据同步完成，DW_P重新加入数据守护系统（可以通过监视器DW_M查看数据守护系统是否恢复正常）；
9. 在DW_M监视器控制台上输入SWITCHOVER命令，重新将DW_P切换为主机，至此滚动升级完成。

## 4.13注意事项

`DM7`数据守护系统较为灵活，系统管理员可根据应用和硬件配置的实际情况进行不同的配置，在决定数据守护配置方案时有一些事项需要注意：

1. 一般建议用户使用非自动切换模式，通过`DW_FAR_ERROR_TIME`参数设置。

2. 不建议使用自动切换方式，如果使用自动切换模式，建议使用监视器确认的方式。在未配置确认监视器情况下，一旦内部网络不可靠或者拔、插主备机连接内部网络的网线，可能导致出现双主机情况，损坏数据库数据。

如果配置了确认监视器，可支持内部网络中断处理，但如果守护进程与确认监视器之间出现网络故障，或者未启动守护监视器，数据守护系统将无法提供自动故障切换功能。

如果内部网络正常，守护进程之间可以正常通信，在自动切换模式下，守护进程不会再通过确认监视器确认远程状态，即使没有确认监视器，也可以正常提供自动故障切换功能，这种情况需要保证内部网络稳定可靠。

3. 守护进程之间、守护进程和监视器之间，既可采用`UDP`也可使用`TCP`方式通信，一个系统内只能使用一种方式，不能同时使用两种方式通信。如果主备需要跨网段，则使用`TCP`方式。

4. 在配置`HA`监控`dmserver`情况下，需要`dmwatch.ini`中设置`INST_AUTO_RESTART`为0，避免`dmwatch`与`HA`软件同时启动`dmserver`实例。

5. 用户应该使用`TAKEOVER`命令将备机切换为主机，不建议用户使用“强制接管”方式将备机切换为主机，避免出现数据损坏。
6. 应该根据磁盘空间情况，合理设置`dmarch.ini`的`ARCH_SPACE_LIMIT`值，防止磁盘空间被归档日志文件占满。

7. 注意`dm.ini`参数`NEW_FILE_POLICY`设置，如果能确保主备机的软硬件环境是完全一致的，建议使用1。如果不能保证，则建议配置为0，使用相对路径策略，采用这种配置策略，所有新创建的数据文件会保存到`dm.ini`中`SYSTEM_PATH`目录下，需要注意`SYSTEM_PATH`所在磁盘空间是否足够。

8. 如果备机重做`redo`日志，创建表空间、文件等操作失败，备机数据库服务器会被强制异常退出。
