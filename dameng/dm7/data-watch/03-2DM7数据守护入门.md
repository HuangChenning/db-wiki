## 2.1 DM7数据守护系统硬件配置

部署`DM7`数据守护的基本硬件包括：

- 主机

用于部署主数据库和守护进程，至少应具备两块网卡，一块接入公共网络，提供数据库服务，一块接入内部网络，传递`REDO`日志和`UDP`消息。

- 备机

用于部署备数据库和守护进程，至少应具备两块网卡，一块接入公共网络，提供数据库服务，一块接入内部网络，接收`REDO`日志，发送并接收`UDP`消息。

由于备数据库分为实时备数据库和异步备数据库，因此通常将部署了实时备数据库的备机称为实时备机（有时直接简称为备机），部署了异步备数据库的备机称为异步备机。

- 监视机

用于部署监视器的机器；可同时配置多个监视器，但最多只能配置一个确认监视器。

- 内部网络

用于主、备机之间传输`REDO`日志，以及守护进程之间、守护进程与监视器之间传递信息。如果条件允许，最好配置多块物理网卡虚拟成一块网卡用于内部网络通信，提升内部网络的吞吐量和可靠性。内部网络通过交换机实现互联，最好能够提供冗余交换机本身，确保内部网络的可靠性。

- 公共网络

用于提供数据库服务的网络环境。公共网络与内部网络应使用不同的交换机。

## 2.2 相关概念

为了更好地理解`DM7`数据守护，先介绍几个与数据同步和故障切换密切相关的概念。

### 2.2.1 REDO日志

`DM7`的重做日志，又叫`REDO`日志，忠实记录了所有物理页的修改，基本信息包括操作类型、表空间号、文件号、页号、页内偏移、实际数据等。数据库中`INSERT`、`DELETE`、`UPDATE`等`DML`操作以及`CREATE TABLE`等`DDL`操作最终都会转化为对某些数据文件、某些数据页的修改。因此，在系统故障重启时，通过重演`REDO`日志，可以将数据库恢复到故障时的状态。

`DM7`服务器可以运行在两种模式下：归档模式和非归档模式，用户可通过设置`dm.ini`配置文件中的`ARCH_INI`参数进行设置。

若设置为非归档模式，则只有联机`REDO`日志。`DM7`产生的`REDO`日志顺序写入联机`REDO`日志文件中，当一个日志文件写满时，自动切换到另外一个`REDO`日志文件；一旦所有文件写满以后，重新写入到起始文件，覆盖老的`REDO`日志内容。所有联机`REDO`日志文件循环使用，永远不会自动增长。

数据守护系统中`REDO`日志必须设置为归档模式（`ARCH_INI`设为1），并根据数据守护系统的具体方案配置不同类型的归档，归档日志的具体配置在配置文件`dmarch.ini`中进行，可参看`2.5.3`节。

`DM7`中与数据守护相关的归档日志类型有：

- `REDO`日志本地归档

`REDO`日志本地归档是在`REDO`日志写入联机日志文件后，将`REDO`日志写入到预先配置的本地归档日志文件的过程。`DM7`最多支持配置8组本地归档。

- `REDO`日志实时归档

`REDO`日志实时归档是在写入联机日志文件之前，通过`MAL`系统将`REDO`日志发送到备数据库，并等待备数据库确认收到`REDO`日志后，再写入联机日志系统的过程。`DM7`最多支持一组实时归档。实时归档只有在数据库为`Primary`模式下才生效。

- `REDO`日志异步归档

`REDO`日志异步归档是指主机上配置的定时器触发时，通过`MAL`系统将`REDO`日志发送到异步备数据库，实现异步备机上的数据同步，`DM7`最多支持8组异步归档。

备数据库收到主数据库发送的实时归档日志/异步归档日志后，进行`REDO`日志重做，即在物理数据页上重演数据修改的过程。重做过程由专门的`REDO`日志重做服务完成，重做服务严格按照收到的`REDO`日志的先后顺序，还原主数据库的修改动作，并在重做过程中生成备数据库自身的联机`REDO`日志和本地归档日志。

### 2.2.2 LSN

`LSN`（`LOG SEQUENCE NUMBER`），即日志序列号，表示`REDO`日志产生的顺序，系统为每个`REDO`日志分配一个`LSN`值。`LSN`是一个64位整数，系统从1开始分配`LSN`值。`REDO`日志`LSN`值是递增的、唯一的，可用来识别数据库的数据变化情况。

守护进程和监视器的`SHOW`命令的显示项中包含几个`LSN`值，分别说明如下。管理员通过查看相关`LSN`值可以判断主备数据库的数据是否一致，若备机的`LSN`大于主机，表示数据守护系统可能已发生错误。

```
- FLSN（FILE LSN）
```

文件`LSN`，已经写入联机重做日志文件的最大`LSN`值。

```
- CLSN（CUR_LSN）
```

系统当前`LSN`，代表已经分配的最大`LSN`值。系统每分配一个`LSN`值，`CUR_LSN`值都会自动加1。

```
- SSLSN（SECOND STANDBY LSN）
```

备机模式下表示数据库收到的主机发送过来的日志的次大`LSN`；主机模式下和`CLSN`相等。

```
- SLSN（STANDBY LSN）
```

备机模式下表示数据库收到的主机发送过来的日志的最大`LSN`；主机模式下和`CLSN`相等。

### 2.2.3 数据库模式与模式切换

`DM7`支持3种数据库模式：`Normal`模式、`Primary`模式和`Standby`模式。

- `Normal`模式：提供正常的数据库服务，操作没有限制。
- `Primary`模式：提供正常的数据库服务，所有数据库对象的修改强制生成`REDO`日志。
- `Standby`模式：用户除对临时表进行增删改及`truncate`操作外，只能只读访问数据库，实时归档失效，但会根据配置，向本地归档文件中写入`REDO`日志。

可以通过执行`SQL`语句完成数据库模式切换，模式切换规则如图`2.2`所示。所有模式转换必须在`Mount`状态下执行。数据守护通过数据库模式的切换实现主数据库和备数据库角色的互换。

### 2.2.4 数据库状态与状态转换

`DM7`支持3种系统状态：`Open`状态、`Mount`状态和`Suspend`状态。

- `Open`状态：正常访问数据库，但不能进行配置操作。
- `Mount`状态：可以执行修改配置文件、控制文件和修改数据库模式等操作，但不能访问数据库对象；`Mount`状态下，系统处于事务一致状态，不存在任何未写入的`REDO`日志和未提交事务。
- `Suspend`状态：挂起所有`REDO`日志写入请求，可以进行只读操作，但不能进行数据库配置，也不能修改数据库模式。

可以通过`SQL`语句实现数据库状态转换，转换规则如下：

- `Open`状态可以直接转换为`Mount`或`Suspend`状态；
- `Mount`状态可以直接转换为`Open`状态；
- `Suspend`状态可以直接转换为`Open`状态；
- `Mount`和`Suspend`状态不能直接转换；
- `Primary`模式下，实时归档失败，系统自动从`Open`状态转入到`Suspend`状态。

### 2.2.5 MAL系统

`MAL`系统是`DM7`数据库服务器的内部高速通信系统，基于`TCP/IP`协议实现。`DM7`服务器的很多重要功能都是基于`MAL`系统实现通信的，例如数据守护、数据复制、`MPP`、远程日志归档等。用户通过配置`dmmal.ini`文件可以对通信的主机、端口等进行设置，具体介绍见`2.5.2`节。

### 2.2.6 OGUID

`OGUID`是数据守护唯一标识码。在配置数据守护时，需要由用户指定`OGUID`值；其中数据库的`OGUID`通过系统函数设置，守护进程和监视器的`OGUID`值在配置文件中设定。

### 2.2.7 守护进程组

配置了相同`OGUID`的主机、备机、守护进程和监视器构成一个守护进程组，至少包括主数据库、备数据库以及它们的守护进程，还可能包括异备数据库与它们的守护进程，以及监视器。一个守护进程组构成了一个完整的数据守护方案。

一个主数据库/备数据库只能属于一个守护进程组，但是一个守护进程可以同时管理多个守护进程组中的数据库实例。如一台计算机上安装了`DM7`数据库实例A、B和C，这三个实例分别属于三个不同的守护进程组，可以在这台计算机上启动一个守护进程同时管理这三个数据库实例，只要在守护进程的配置文件`dmwatch.ini`中配置清楚每个守护进程组的相关参数即可。

为方便管理，对每个守护进程组进行命名，称为守护进程组名。守护进程组中的所有守护进程和监视器，必须配置相同的组名。

## 2.3 理解DM7数据守护系统架构

本书`1.1`节中介绍了数据守护系统的架构，可以看到`DM7`数据守护系统包含的主要部件有主数据库、备数据库（包括异备数据库）、`REDO`日志系统、`MAL`系统、守护进程和监视器。其中`REDO`日志系统和`MAL`系统实际上是集成在`DM7`服务器中的功能模块，在`2.2`节中已经进行了介绍。下面主要介绍主数据库、备数据库、守护进程和监视器这几个数据守护系统中较为独立的几个部件。

### 2.3.1 主数据库

主数据库是数据守护系统中对外提供生产服务的数据库，应用连接到主数据库进行正常的增、删、改、查操作，操作过程与在普通单机版数据库上没有区别。

与普通单机版数据库相比，数据守护系统的主数据库需要被设置为`Primary`模式，同样也有`Mount/Open/Suspend`三种状态。在`OPEN`状态下，用户可以正常对数据进行各种操作，所有对数据库对象的修改生成`REDO`日志，在归档有效时，通过`MAL`系统发送`REDO`日志到备机重做。

对于实时备数据库，主数据库在写入本地`REDO`日志文件之前，先将缓存中的日志发送给实时备数据库，待收到备数据库响应后再刷盘，保证备数据库和主数据库的数据实时同步。

对于异步备数据库，主数据库根据定时器配置的时间间隔发送日志给备数据库进行重做，因此异备数据库可能会和主数据库的数据有一段日志差。

### 2.3.2 备数据库

数据守护系统中的备数据库处于`Standby`模式，是主数据库的备份库。备数据库只有`Mount`和`Open`两种状态，并且只允许用户进行只读操作。备机接收主机发送过来的`REDO`日志并重做，在解析重做`REDO`日志时，直接在对应数据页的对应偏移上写入最新数据，在物理层面上实现与主机数据的同步。

备数据库分为实时备数据库和异备数据库：

- 实时备数据库与主数据库的数据实时同步，主数据库使用`REDO`日志实时归档方式向实时备数据库发送`REDO`日志，一个数据守护系统最多只能有一个实时备数据库；
- 异备数据库与主数据库之间的数据会有一段日志差，主数据库使用`REDO`日志异步归档方式向异备数据库发送`REDO`日志，一个数据守护系统最多能配置8个异步备数据库。

用户可以通过只读访问备数据库来减轻主数据库的负载。

### 2.3.3 守护进程

守护进程（`dmwatch`）是实现数据守护方案的关键组件，是`DM7 SERVER`外的独立工具。数据守护方案中的每个`DM`数据库实例都要配备一个自己的守护进程，守护进程与其所监控的数据库实例必须部署在一台计算机上。

守护进程在数据守护方案中的主要作用有：

| 􀁺 监控数据库状态 | 监控数据库运行状态，必要时重启数据库服务 |
| --- | --- |
| 􀁺 广播状态信息 | 广播自身和其所监控数据库的运行状态信息 |
| 􀁺 接收守护进程消息 | 接收远程守护进程的TCP或UDP广播信息，结合自身状态，在需要时切换数据库的运行模式和系统状态 |
| 􀁺 接收监视器消息 | 接收监视器的TCP或UDP广播消息，通知数据库进行主备数据库角色转换、启动或关闭监控功能 |
| 􀁺 切换数据库角色 | 在主数据库或者主机出现故障时，负责将备数据库切换为主数据库，继续对外提供数据库服务 |
| 􀁺 管理实时归档日志 | 在备数据库或者备机出现故障时，负责将主数据库的实时归档失效，使主数据库能够继续提供数据库服务 |
| 􀁺 同步历史数据 | 在故障排除后，通知主数据库同步本地归档REDO日志到备数据库，并在历史数据同步完成后，恢复主数据库的REDO日志实时归档功能，将数据守护系统恢复到可提供故障自动切换的状态 |
| 􀁺 守护进程命令 | 可以在守护进程的控制台上输入命令，关闭守护进程、显示 守护进程组的状态信息等，具体命令参考表2.1 |

表`2.1` 守护进程命令

| 命令 | 含义 |
| --- | --- |
| HELP | 帮助 |
| EXIT | 关闭守护进程 |
| STATUS | 显示守护进程运行状态 |
| SHOW | 显示守护进程及其监控数据库的状态信息 |

用户通过配置文件`dmwatch.ini`对守护进程进行设置，具体配置文件介绍见`2.5.4`节，下面主要介绍守护进程的工作模式和状态。

- 守护进程模式

守护进程有三种不同的工作模式，可通过`dmwatch.ini`的`DW_MODE`参数进行设置，工作模式在守护进程运行中不能动态改变。

- 本地模式

监控本地数据库服务，如果连续一段时间没有收到来自其监控数据库的`UDP`消息，即认定数据库出现故障；一旦检测到数据库故障，试图使用配置的启动命令，重启数据库服务，功能比较单一。

- 切换模式

在本地模式基础上，增加了切换主备数据库角色的功能，不但监控本地数据库服务，还接收来自远程守护进程的`TCP`或`UDP`消息。

该模式包含自动切换模式和非自动切换模式两种，通过`dmwatch.ini`的`DW_FAR_ERROR_TIME`参数设置来区分。`DW_FAR_ERROR_TIME`为0时表示非自动切换，大于0时表示自动切换。自动切换模式下支持故障自动处理，非自动切换模式下，需要通过监视器命令完成故障处理。

- 异步备机守护模式

异步备机的守护进程需要配置为此模式，该模式下守护进程只负责监控本地实例，处理远程主机的`UDP`消息以及广播本地实例状态，不处理监视器命令消息。

- 守护进程状态

守护进程运行中根据整个数据守护系统的变化会自动或通过管理员手动进行状态转换，具体有以下九种状态。

- `Startup`状态：守护进程启动状态，在切换模式下，需要根据远程守护进程发送的状态信息，结合本地数据库的初始模式、状态和数据同步情况，确定本地数据库的启动模式和状态后，进入`Open`状态。
- `Open`状态：守护进程正常工作，监控数据库，并定时发送数据库的状态信息，接收其他守护进程发送的信息，接收监视器发送的用户请求。
- `Shutdown`状态：守护进程停止监控数据库状态，也不提供主备机切换功能。
- `Switchover`状态：手工切换主备机过程中，守护进程设置为`Switchover`状态。
- `Failover`状态：故障切换过程中，守护进程设置为`Failover`状态。
- `Recovery`状态：故障恢复同步历史数据过程中，守护进程设置为`Recovery`状态。
- `Confirm`状态：通过监视器确认远程主（备）机是否活动的过程中，守护进程设置为`Confirm`状态。
- `Takeover`状态：非自动切换模式，主机确认故障后，备机手工接管过程中，守护进程设置为`Takeover`状态。
- `Open force`状态：非自动切换模式下，备机不启动，只希望启动主机以异步方式工作。监视器强制启动主机过程中，守护进程设置为`Open force`状态。这里的主机异步工作方式，指主机可以正常工作，但产生的日志不会实时同步到备机，主备机之间有日志差。等备机恢复正常工作时，主机会将这段时间的日志一并发给备机进行重做，重新实现主备机的实时同步。

其中，`Startup`和`Open`是两个基本状态，在满足一定条件时，守护进程会转换为其他状态，待状态处理完成后又重新回到`Open`或`Startup`状态，如果关闭守护进程的监控功能，则会一直处于`Shutdown`状态。

`Open`状态下满足一定条件会转入`Failover/Switchover/Takeover/Recovery`中的一种状态，状态处理成功后重新回到`Open`状态，处理失败则回到`Startup`状态；`Failover/Switchover/Takeover/Recovery`状态之间不能互转，`Confirm`状态下满足条件时会转入`Failover`状态，状态的转换规则如下图所示。

### 2.3.4 监视器

监视器（`dmwmon`）是`DM7`数据守护方案的一个可选工具，部署在独立的第三方机器上。监视器分为普通监视器和确认监视器两种模式，一个数据守护系统中可以配置多个监视器，但是最多只能配置一个确认监视器。

监视器在数据守护系统中具有以下功能：

| 􀁺 监视数据守护状态 | 接收守护进程发送的消息，显示主、备数据库状态变化，以及故障切换过程中，数据库模式、状态变化的完整过程 |
| --- | --- |
| 􀁺 控制数据守护状态 | 用户可以在监视器上输入命令，启动、停止守护进程的监控功能，将主备数据库的角色互换等 |
| 􀁺 状态信息确认 | 这是确认监视器独有的功能。当守护进程接收不到远程守护进程的TCP或UDP消息时，可通过监视器来确认对方的状态信息。监视器转发状态信息，作为守护进程的决策依据。 |

用户可通过`dmwmon.ini`配置文件中的`MON_DW_CONFIRM`参数设置监视器的工作模式，配置文件中还可设置监视器的其他一些工作参数，具体见`2.4`节的介绍。

监视器为控制台工作界面，可以直接输入命令，监视器支持的命令见表`2.2`。其中执行以下操作都要求先登录监视器，登录口令与服务器的登录口令一致，且要求必须有数据库的`DBA`权限：

```
- STOP ALL/STOP 实例名
- INST EXIT ALL/INST EXIT 实例名
- SWITCHOVER/TAKEOVER/OPEN FORCE
```

- 确认监视器

与普通监视器不同，确认监视器会定时收集数据守护系统中主机与备机的状态信息，并把这些状态信息发给守护进程。守护进程可根据自己采集的信息以及收到的确认监视器发来的信息综合决定故障处理流程。

我们强烈建议若用户的数据守护系统采用自动切换模式，且不能保证内部网络非常稳定的情况下，务必为守护系统配置一个确认监视器，以防止守护系统出现双主机。

所谓双主机，就是在同一个守护系统中，由于网络不稳定或人为因素等原因，在主机正常的情况下，实时备机也切换为主机对外提供服务，系统中同时出现两个主机的情况。双主机的情况下，两个主机都可以接收外部应用连接，就会出现数据不一致的情况，导致数据被破坏。

## 2.4 DM7数据守护系统中的信息传递

`DM7`数据守护方案的核心是信息的传递，以及根据获取到的信息进行相应决策的过程，信息以`TCP`和`UDP`相结合的方式，在主备数据库、守护进程、监视器之间相互传递，并最终达到状态监测、控制和角色转换等目的。信息在以下几个进程之间传递：

- 主数据库与备数据库

主数据库通过基于`TCP`协议实现的`MAL`系统，发送`REDO`日志到备数据库，`REDO`日志包括运行产生的实时归档日志和恢复时的本地归档日志。

- 数据库与守护进程

主（备）数据库定是以`UDP`消息的方式，向本地守护进程发送数据库模式、数据库状态、实时归档状态、当前已写入联机日志文件的`LSN`（`FLSN`）值，最新的`LSN`（`CLSN`）值等信息；如果是备数据库，还发送已收到`REDO`日志中最大`LSN`值（`SLSN`）以及次大的`LSN`值（`SSLSN`）。

- 守护进程与数据库

守护进程定是以`UDP`消息的方式，通知其监控的数据库守护进程本身是活动的。当满足切换条件时，发送模式切换、状态转换、发送归档日志等消息给数据库。数据库只接收本地守护进程的`UDP`消息，不接收远程守护进程的`UDP`消息，也不接收监视器的`UDP`消息。

- 守护进程与守护进程

守护进程之间支持`TCP`和`UDP`两种通信方式，守护进程收到数据库发送的`UDP`消息后，解析并保存数据库状态信息；并定时将这些信息以`TCP`或`UDP`广播形式发送出去。守护进程相互接收对方发送的信息，结合自身信息进行自主决策，执行故障处理等操作。

- 守护进程与监视器

守护进程和监视器之间也支持`TCP`和`UDP`两种通信方式，如果选用`UDP`方式，则要求守护系统部署在同一局域网内，否则监视器无法收到守护进程的`UDP`广播消息；如果选用`TCP`方式，则允许跨网段部署。监视器只接受守护进程的`TCP`或`UDP`消息，不接收数据库的任何消息。

- 监视器与守护进程

监视器也可以通过广播`UDP`或定时发送`TCP`消息，向守护进程传递启动监控、停止监控、切换主备数据库等命令。

由于`UDP`协议无法像`TCP`协议一样提供可靠的通信保障，因此`DM7`数据守护采用了多次确认的方式，只有连续多次未收到`UDP`消息的情况下，才认定为故障，认定故障的时间可在`dmwatch.ini`中配置。

## 2.5 相关配置文件

与`DM7`数据守护相关的配置文件包括：

- 数据库配置文件`dm.ini`
- `MAL`系统配置文件`dmmal.ini`
- `REDO`日志归档配置文件`dmarch.ini`
- 守护进程配置文件`dmwatch.ini`
- 监视器配置文件`dmwmon.ini`

其中`dmmal.ini`和`dmarch.ini`必须与`dm.ctl`使用相同目录，`dm.ctl`存放目录在`dm.ini`的`CTL_PATH`配置项中指定，下面对这些配置文件一一进行介绍。

### 2.5.1 dm.ini数据守护相关配置项

`dm.ini`是`DM7`数据库实例的配置文件，通过配置该文件可以设置`DM7`数据库服务器的各种功能和性能选项。`dm.ini`中的配置项多达数百个，涉及`DM7`数据库运行各个方面的设置，这里我们只介绍与数据守护相关的几个配置项，读者若对其他配置项感兴趣可以参看《`DM_DBA`》。

- 守护进程通信方式说明

守护系统中，守护进程和本地实例、远程守护进程、监视器之间都有通信，其中守护进程和本地实例之间使用`UDP`方式定向发送消息，守护进程之间、守护进程和监视器之间支持`TCP`和`UDP`两种通信方式，其中`UDP`方式支持广播和组播配置，广播方式需要守护系统部署在同一个局域网内，组播方式和`TCP`方式同时支持单个局域网和跨网段部署。

`TCP`及`UDP`相关的配置参数请参考表`2.6`的说明，如果同时配置有`TCP`和`UDP`参数，则选择`TCP`方式进行通信。守护进程之间、以及守护进程和监视器之间的通信方式需要保持一致，都使用`TCP`或都使用`UDP`方式，否则守护系统无法正常使用。

- 守护进程判断实例故障说明

如果配置有`DW_DM_INI`路径，且`dm.ini`中`HA_INST_CHECK_FLAG`配置为1，则会检查`SYSTEM_PATH`路径下的心跳文件`dminst.sys`，判断实例是否处于活动状态。

心跳文件`dminst.sys`是用来检测`DM`服务器`dmserver`是否活动的文件，文件中记录有一个序列值，在`HA_INST_CHECK_FLAG`配置为1且实例正常运行的情况下，序列值每秒钟递增一次，如果超出`DW_INST_ERROR_TIME`配置的时间，序列值仍然没有变化，则认为心跳检测失败。

如果出现下面任意一种情况，则守护进程认定实例故障，修改实例状态为`ERROR`。

- 守护进程根据实例广播出来的进程号，检查对应的实例进程已经不存在，则认定实例出现故障，修改实例状态为`ERROR`；
- 实例进程还在，守护进程超过`DW_INST_ERROR_TIME`配置的时间未收到实例消息，且`dminst.sys`心跳检测失败，则认定实例出现故障，修改实例状态为`ERROR`；
- 实例进程还在，守护进程超过`DW_INST_ERROR_TIME`配置的时间未收到实例消息，如果没有配置`DW_DM_INI`或`HA_INST_CHECK_FLAG`不为1，则不检查`dminst.sys`文件，直接认定实例故障，修改实例状态为`ERROR`。
- 组播配置说明

数据守护系统支持跨网段配置，守护进程之间、守护进程和监视器之间的通信可跨网段进行。可采用`TCP`或`UDP`组播配置方式，`UDP`组播方式条件比较严格，一般建议使用`TCP`方式。

使用`UDP`组播方式的注意事项如下：

1) 单个局域网内支持组播方式配置，不需要支持组播协议；

2) 跨网段配置时，连接不同网段的路由器、交换机等设备必须能够支持组播协议，并打开相关组播协议；

`3)` 组播组内的主机如果没有组播路由，则需要添加组播路由到路由表中，且需要保证添加组播路由时绑定的网卡设备`IP`地址协议和组内其他主机一致，都使用`IPV4`或`IPV6`协议。

以下简单介绍一下`Linux`和`AIX`操作系统中添加组播路由的命令（不同操作系统命令格式可能不同，需要根据实际情况调整）。

```
1. 操作系统Linux localhost.144 2.6.32-220.el6.x86_64，添加路由命令：
route add -net 224.0.0.0 netmask 240.0.0.0 dev eth0
```

该命令将D类组播地址`224.0.0.0`加入到路由表中，子网掩码`240.0.0.0`，绑定网卡设备`eth0`，即组播消息通过设备`eth0`发送和接收，同一个多播组中绑定的设备支持的`IP`协议需要一致。

此处添加的是动态路由，系统重启后需要重新添加，可以将此命令添加到`/etc/rc.local`文件，系统启动后自动执行。

2. 操作系统`AIX 7.1-64`，添加路由命令：

```
route add -net 224.0.0.0 192.168.0.196 -if en0
```

该命令将D类组播地址`224.0.0.0`加入到路由表中，网关地址`192.168.0.196`，绑定网卡设备`en0`，即组播消息通过设备`en0`发送和接收。

此处添加的是动态路由，系统重启后需要重新添加，`AIX`可以通过自带的`smit`工具，使用`smit mkroute`命令进入配置界面，增加为静态路由。

查看路由表命令：

```
netstat –rn
Kernel IP routing table
Destination Gateway Genmask Flags MSS Window irtt Iface
224.0.0.0 0.0.0.0 240.0.0.0 U 0 0 0 eth0
```

守护进程或监视器启动后，可以查看加入的多播组信息与网卡设备是否一致，下面示例中守护进程配置的组播地址为`234.1.1.1`，与设备`eth0`关联。

查看多播组命令：

```
netstat -gn
IPv6/IPv4 Group Memberships
Interface RefCnt Group
--------------- ------ ---------------------
eth0 1 234.1.1.1
```

- `DW_BRO_ADDR`配置说明

`DW_BRO_ADDR`参数用来配置`UDP`广播或组播地址。

组播方式不需要计算此地址，同一套守护系统中设置统一的组播地址即可，取值范围为`(224.0.0.1~239.255.255.255)`。注意不能使用保留地址。用户一般使用范围`224.0.1.0~238.255.255.255`。

广播方式可以使用`DM7`的系统函数`SF_GET_BROADCAST_ADDRESS()`来获取广播地址。假定`MAL_HOST`配置项的值为`15.16.193.6`，子网掩码是`255.255.248.0`，下面示例说明了如何获取广播地址。

```
select sf_get_broadcast_address('15.16.193.6','255.255.248.0');
SQL>select sf_get_broadcast_address('15.16.193.6','255.255.248.0');
行号 SF_GET_BROADCAST_ADDRESS('15.16.193.6','255.255.248.0')
---------- -------------------------------------------------------
1 15.16.199.255
```

该系统函数使用的是如下的算法：

把`IP`地址和子网掩码都换算成二进制数，两者进行逻辑与运算后得到网络地址，根据子网掩码中主机地址全部为0的部分，在网络地址对应位中全部置成1，即得到广播地址。如示例中`MAL_HOST`配置项值为`15.16.193.6`，子网掩码是`255.255.248.0`，计算广播地址算法步骤如下：

`1)` 换算`IP`地址为二进制，得到网络地址为：

```
00001111.00010000.11000001.00000110
```

`2)` 换算子网掩码为二进制，得到子网掩码为：

```
11111111.11111111.11111000.00000000
```

`3) IP`与子网掩码相与后，得到网络地址：

```
00001111.00010000.11000000.00000000
```

`4)` 将掩码中为0的位在网络地址中置成1，得到广播地址：

```
00001111.00010000.11000111.11111111
```

`5)` 最后，换算成十进制，得到`DW_BRO_ADDR`值为：

```
15.16.199.255
```

- `INST_STARTUP_CMD`配置说明：

`INST_STARTUP_CMD`用来配置守护进程在此守护进程组中监控的数据库实例的启动命令，用于在需要的时候启动对应的数据库实例。根据不同的操作系统和以命令行或是服务方式启动数据库实例，该参数应配置为不同的命令，以下是几个常用场景的例子。

`1) linux`命令行方式启动（不能出现带有空格的路径）：

```
INST_STARTUP_CMD = /opt/dm/bin/dmserver /opt/dm/data/dm.ini
```

`2) linux`服务方式启动：

```
INST_STARTUP_CMD = service dmserverd restart
```

`3) Windows`命令行启动：

```
INST_STARTUP_CMD = c:\dm\bin\dmserver c:\dm\data\dm.ini
```

`4) Windows`服务方式启动:

`INST_STARTUP_CMD = net start` 注册服务名（注册服务名，可通过`DM`服务查看器获取）

### 2.5.5 dmwmon.ini

`dmwmon.ini`是监视器的配置文件，具体配置项介绍见表`2.7`。

```
表2.7 dmwmon.ini配置项
```

| 配置项 | 配置含义 |
| --- | --- |
| MON_UDP_TYPE | UDP通信方式，0表示广播方式，1表示组播方式，默认为0 |
| MON_UDP_TTL | 数据包生存期，数据包传送时最大可经过的路由器个数，取值范围为1到128，默认为3。 |
| MON_BRO_ADDR | UDP广播地址或组播地址，与dmwatch.ini中DW_BRO_ADDR保持一致 |
| MON_UDP_PORT | UDP广播端口，与dmwatch.ini中DW_UDP_PORT保持一致 |
| MON_DW_TCP_PORT | TCP方式下，连接远程watch的TCP端口，和dmwatch.ini中的DW_TCP_PORT保持一致 |
| MON_DW_IP | TCP方式下，远程守护进程地址，和dmmal.ini中的MAL_HOST保持一致，该配置项最多允许配置10个（实时主备机和8个异步备机），对应多个远程watch地址，不允许有重复值。 |
| MON_INST_OGUID | 数据守护唯一标识码，与dmwatch.ini中的INST_OGUID 保持一致 |
| MON_GROUP_NAME | 守护进程组名，与dmwatch.ini中的守护进程组名保持一致 |
| MON_DW_CONFIRM | 确认监视器配置，0为普通监视器，1为确认监视器；缺省为0 |
| MON_LOG_PATH | 日志文件路径，日志文件命名方式为“dmwmon_端口号_年月日时分秒.log”，例如“dmwmon_55681_20150418230523.log”。 若MON_LOG_PATH没有配置则日志文件使用dmwmon.ini配置文件所在的路径作为日志文件路径 |
| MON_LOG_INTERVAL | 自动记录系统状态信息到日志文件的时间间隔，取值0,1，或(5~3600)，单位秒。0表示不记录任何日志，此时MON_LOG_FILE_SIZE 和MON_LOG_SPACE_LIMIT 不起作用；1表示只记录监视器正常接收到的消息；5~3600表示除了记录监视器正常接收消息外，每隔指定的间隔另外记录系统信息到日志文件中。默认值为1 |
| MON_LOG_FILE_SIZE | 单个日志文件大小，范围16~2048，单位为M，默认值为64，达到最大值后，会自动生成并切换到新的日志文件中，如果达到设定的总空间限制，会自动删除创建时间最早的日志文件。 |
| MON_LOG_SPACE_LIMIT | 日志总空间大小，取值0或者256~4096，单位为M，默认值为0，表示没有空间限制 |

在自动切换模式下，同一守护进程组中监控主机与实时备机的两个守护进程的`DW_MON_CONFIRM`配置项值必须相同，要么都为0，要么都为1；如果配置为1，则必须配置一个确认监视器，并且只能配置一个确认监视器；如果配置了多个确认监视器，在发生网络故障时，将会出现双主机，导致数据损坏。

如果配置有确认监视器，只有在本地守护进程接收不到远程守护进程的`TCP`或`UDP`消息时,才需要通过确认监视器来确认对方的状态信息，此时需要保证本地和远程守护进程到确认监视器之间的网络通信正常，否则也无法通过确认监视器来确认状态。在自动切换模式下，如果守护进程之间的网络通信正常，守护进程在自动处理各种故障情况时，不会再通过确认监视器来确认状态，即使不启动确认监视器，也可以正常完成切换，但需要保证内部网络可靠稳定。

`TCP`相关的配置参数为`MON_DW_TCP_PORT`和`MON_DW_IP`，其中`MON_DW_IP`允许配置多个，指定所有远程守护进程的`IP`地址。只要配置了`TCP`参数就以`TCP`协议进行通信，会忽略`UDP`参数，未配置`TCP`参数才使用`UDP`协议，至少要配置一种方式。

守护进程和监视器之间的通信方式需要保持一致，都使用`TCP`或都使用`UDP`方式，否则守护系统将无法正常使用。
